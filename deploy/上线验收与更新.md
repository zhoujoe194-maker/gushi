# 上线验收与日常维护

适用版本：2026-11-02；数据库迁移 0000–0010，共 11 个。单实例 Node.js 24 + SQLite。本文不包含真实密码、启用码或公司数据库。

## 第一次上线

按根目录《部署说明.md》配置正式域名、HTTPS、持久化数据卷和 `.env.production`。保持部署目录和 Docker Compose 项目名称固定，例如 `/opt/gushi-workspace`；更换目录或项目名称可能连接到另一组空数据卷。

```sh
cd /opt/gushi-workspace
docker compose build
docker compose up -d
docker compose ps
docker compose logs --tail=100 web
docker compose exec -T web node scripts/selfhost-healthcheck.mjs
```

通过标准：容器为 healthy；探针返回“服务与数据库就绪”；日志没有迁移失败。访问正式 HTTPS 域名的 `/api/health` 应返回 HTTP 200 和 `{"status":"ok"}`；未就绪返回 503。接口不返回人员、数据库位置或配置。健康检查验证应用能读数据库及最新迁移，不能代替备份完整性、磁盘容量和真实业务验收。

首位管理员邮箱为 `admin@example.com`。打开网址，在首次启用页面输入部署负责人提供的随机启用码、本人真实姓名并设置个人密码，无需额外创建管理员命令，也没有统一初始密码。成功后从部署配置移除启用码并重新创建容器，使配置生效；已有账号时初始化入口始终关闭。

管理员通过人员管理开通员工邮箱或手机号、默认工作台和一个或多个工作台权限（原分部字段仅作历史数据保留）。员工首次登录确认姓名、修改初始密码。岗位由管理分配，没有公开自助选岗位注册；初始密码通过公司内部渠道单独交付。

## 上线当天的业务验收

先在隔离的测试部署练习全流程，再在正式环境使用明确标注的测试项目及测试成员做小范围核验，完成后停用测试成员。不要在正式数据库运行 `tests/` 自动验收脚本。

| 场景 | 操作与通过标准 |
| --- | --- |
| 账号与岗位 | 新员工实名改密；单台直达、多台选择；无权限台打不开；停用或调整权限后旧会话失效。 |
| 项目协作 | 销售建项目、填写下一步及日期；对应岗位按权限处理交接；无权限员工不能读取越权项目、工资费用与公司现金详情。 |
| 独立任务 | 下发任务，指定承办台/人及期限；保存进展、上传图片、提交；管理退回说明原因，补充后再次提交验收。 |
| 消息与群聊 | 私聊、台消息、项目群均可收发；移出群的成员不能继续读取；消息不会自动变成任务。 |
| 合同与票款 | 提交合同、财务审核或退回；维护应收、回款及开票申请；核对余额和状态；售后/运营不能读票款内部信息。 |
| 销售工作记录 | 员工提交工作依据，管理核实或退回，保留历史。 |
| 周报与月报 | 分类数量、说明、总结及计划可提交；合计和电话数校验正确；导出包含新字段；未填数量与 0 区分。 |
| 月度绩效 | 员工自评；清理待审核记录；月份结束后管理评分发布；发布后锁定；修正时先退回绩效，再补充并重审。 |
| 手机与异常 | 手机上传并查看任务图片、填写报表；键盘可操作表单；断网提交有提示；恢复后重试并核对状态；销售表单误关闭前有确认。 |

销售考核只覆盖工作记录、周报、月报及绩效，不包含定位打卡或上下班考勤。周报截止为北京时间周六 24:00；月报尚未规定统一截止日。待审核内容阻止发布；退回内容不阻止管理依据实际情况核分。缺失记录不会自动视为完成。

## 备份与监控

```sh
cd /opt/gushi-workspace
docker compose exec -T web node scripts/selfhost-backup.mjs
```

脚本通过 SQLite 在线备份生成一致副本，并打印容器中的备份路径。备份含账号摘要、项目、聊天和任务图片，保存在 `company_backups` 卷；并非自动存到服务器外。将打印出的文件复制到受控备份位置：

```sh
# 把占位文件名换成上一步输出；宿主机目录应仅管理员可读。
umask 077
mkdir -p /srv/gushi-backups
docker compose cp web:/app/backups/实际备份文件名.sqlite /srv/gushi-backups/
```

每天至少备份一次，升级前额外备份；另存到另一台服务器或公司受控存储，定期在隔离环境恢复。不能只复制运行中的 `company.sqlite`，否则可能漏掉 WAL 中的新数据。

可由运维把以下行放入有 Docker 权限的维护账号的 crontab（先人工执行成功，路径按实际环境调整）。本交付不会自动修改服务器计划任务：

```cron
15 2 * * * cd /opt/gushi-workspace && /usr/bin/docker compose exec -T web node scripts/selfhost-backup.mjs >> /var/log/gushi-backup.log 2>&1
```

确认 Docker 路径及日志写入权限，配置日志轮转。示例仅做本机备份，还需安排异地复制、失败通知及保留周期；长期不清理会占满磁盘。确认恢复副本有效后再清理旧备份。

监控至少涵盖：HTTPS 健康接口失败、容器退出或反复重启、磁盘空间、超过一天未成功备份、证书到期。Docker 健康状态本身不会触发 `restart: unless-stopped` 重启；该策略处理进程退出，持续 unhealthy 需告警并检查日志。

## 以后修改代码如何更新

后续更新源码和构建，继续使用原 `.env.production`、数据卷及数据库路径。不要上传本机数据库覆盖正式库，不执行 `docker compose down -v`，不修改或删除旧迁移文件。

1. 在测试部署验收新版本，保留旧源码/镜像及配置的安全副本。
2. 通知同事短暂停止提交。保持同一个部署目录和 Compose 项目名，更新源码，保留服务器环境文件及数据卷。
3. 先构建镜像；失败时旧容器仍可运行，不切换。
4. 构建成功，在旧服务运行但业务停写时做在线备份，核对结果并另存服务器外，记录备份时间。
5. 启动新镜像，自动应用新增迁移；确认健康及业务验收通过后恢复使用。

```sh
cd /opt/gushi-workspace
docker compose build
docker compose exec -T web node scripts/selfhost-backup.mjs
# 核对并另存备份后继续
docker compose up -d --no-build
docker compose ps
docker compose exec -T web node scripts/selfhost-healthcheck.mjs
docker compose logs --tail=100 web
```

随后核对管理员登录、原项目与消息、旧周报、任务图片、新报表提交及管理审核。含数据库结构变更的版本不能只回退程序，旧代码可能不认识新类型。

直接 Node 部署保留同一个绝对 `DATABASE_PATH`：先备份，在新源码目录安装依赖及构建，停旧进程，再使用相同生产环境运行 `npm start`，检查健康与业务。用 systemd 等进程管理器长期运行。

## 故障与恢复

- 健康失败：检查日志、配置、磁盘空间、数据卷挂载和迁移错误，不要新建数据库来掩盖故障。
- 迁移失败：停止发布，保留日志和原数据。已执行迁移的校验不一致时先核对版本。
- 确需恢复：先停止业务和应用，在受控位置保存故障数据库及 WAL/SHM；核验备份完整性和对应的旧程序；用备份替换数据库，处理旧 WAL/SHM，确保权限正确，再启动并核对。先在隔离目录演练，不对运行中的数据库直接覆盖。
- 恢复备份会丢失备份之后的新增修改，先核对补录方案。普通代码更新不需要恢复数据库。

## 开发人员的完整复验

```sh
npm ci
npm run build
RUN_LOCAL_TESTS=1 npm run test:release
```

测试自动为每组用例创建新隔离数据库，默认用本机 5210–5218 端口，报告在 `work/release-checks/run-*/summary.json`；可用 `QA_BASE_PORT`、`QA_OUTPUT` 调整。测试机器需允许在 `/private/tmp` 创建目录（Linux 可由运维事先准备并授权）；只在开发/验收机器运行。

覆盖权限、首次启用、账号人员、项目、任务及图片、消息群聊、销售考核、生产路由资源、备份恢复及历史报表迁移。不替代目标 Linux Docker 构建、真实 HTTPS、外网连通性及并发容量验收。
