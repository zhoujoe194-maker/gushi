# 第三阶段 C：项目收支与现金流

## 复用方案

客户收款计划和实际到账沿用 `finance_books.plans/receipts`；采购付款沿用 `finance_books.suppliers/payments`；订单、报销作为同一项目台账的扩展。交付批次沿用项目 `execution.batches`。合同总额和订单总额是核对上限/业务信息，不独立计入现金流。

银行流水仅记录一次银行业务与分摊关系，实际金额仍由原项目记录及公司费用支付明细汇总，不能再叠加银行流水金额。新增的公司费用只覆盖原项目账本不含的工资、租金等业务。所有计划和核销具有稳定 ID，变更保留审计；金额输入转为整数分，汇总检查安全整数上限。

`0013_cashflow.sql` 为增量迁移，不删除或重写原表。每次跨项目核销在一个事务里验证全部相关版本，写银行流水和各项目余额；任何失败整体回滚。重复请求 ID、银行流水号、同笔重复分摊及超额核销均受校验。

## 数据计算口径

1. 所有收支金额以整数分保存；输入的小数金额按字符串拆分转换，累计验证安全整数边界。合同总额、采购订单总额和发票金额都不作为实际现金流再次累计。
2. 项目待收/待付 = 对应计划金额 − 有效实际核销金额。部分核销只减少对应业务 ID；冲销保留原流水并恢复相应余额。银行流水分摊总和必须等于流水总额，同笔不能重复分摊到同一计划，不能混合收入和支出。
3. 原合同页面与新项目收支共用 `finance_books`。先建项目回款计划再审合同时，沿用原计划 ID、已有到账和变更信息；已审核合同不能再确认超额收款计划。新采购必须关联订单与有效交付批次，订单总额不再次计入现金流。
4. 报销待处理或驳回不进入预测；确认待支付进入预测，部分支付后只计剩余，支付完成后只保留历史实付。报销授权是独立窄权限，不自动开放项目动态、聊天、合同或其他成员报销。
5. 公司费用草稿/取消不进入预测。工资复制先为草稿，财务确认后生效。工资和实际发薪用同一个计划 ID；勾选结清后不再预测预算差额，原预算和实发金额都保留。高于预算的实付须明确结清；预算调整保留旧值。
6. 工资所属月份用于归属，预测使用实际预计发薪日。周期费用当前按月生成，最多 24 期，日期按月末收敛，例如 30 日在二月为 28/29 日，不自动无限续期。工资标记已含社保、公积金时，同月对应费用不能再次确认。
7. **期初余额是指定日期零时余额**。当前现金 = 期初 + 从该日到今天的有效实际收入 − 同期实际支出。期初之前的流水不再叠加；没有期初时余额显示“待设置”，不虚构资金充足结论。请勿将已包含当天流水的日末余额作为当日零时余额。
8. 未来 13 周从今天开始，每周连续 7 天，共 91 天；30 天指标包含今天至第 30 天。每周展示收支、期末余额及周内日末最低余额。逾期仍未核销的计划临时放在今天，并明确标记逾期，财务应尽快核实新的日期。
9. 保守：只计已确认回款；基准：已确认加预计回款；乐观：再加不确定回款。三种情景都计入已确认费用计划的剩余支出，即使预计日期存在不确定性，也不乐观删除成本。草稿与不确定回款的排除原因可在页面查看；不使用未经确认的概率折算。
10. 货期付款规则：预付款/分期付款使用明确的财务日期；发货前付款为发货日期减提前天数；到货付款为到货日加账期；验收后为验收日加账期；月结为到货次月指定日（月底收敛）加约定天数。优先真实发货/到货/验收日期，否则使用预计日期。变更货期只更新建议，财务确认前仍按原日期预测，不修改已付流水。
11. 项目垫资与公司银行余额分开计算：累计项目实际净收付，再叠加所选情景中 13 周内的未收付款，负累计金额的峰值为最大垫资。按同日净额计算，避免行排序制造虚假缺口；占用时间是累计为负的天数，期末未回补标记“至少”。它是现金占用分析，不是利润、成本核算或绩效评分。
12. 银行流水号应使用包含银行账户标识的唯一编号。整体冲销用于纠正登记错误；不是自动操作银行退款。银行记录只保留业务核销及来源关系，现金流从计划实际明细读取，不把银行记录再加一次。

## 兼容性、当前边界

- 旧财务数据、项目、账号、消息和任务均保留。旧计划默认沿用原日期；未关联采购订单的旧应付有提示，不擅自为它们编造采购条件。可从项目收支选择原计划，补充订单和批次，保留原支付历史。
- 新增迁移已在原 B 模拟库的副本和空库验证；备份恢复包含新增表。SQLite 凭证与台账一同备份。正式使用前仍需财务核实期初余额、历史未结余额和银行唯一编号习惯。
- 所有操作是财务人工核实后的登记，不连接真实银行、不发起转账。预测依赖已经录入的计划，未录入费用和同日银行处理先后无法自动推断。
- 报销凭证当前每条支持一个 PNG/JPEG/PDF，最大 2MB；管理分类编辑、自动银行导入及多币种不在本阶段。
- 真实员工、真实手机设备与银行对账未做人工验收；浏览器自动化采用桌面 Chrome 和 390px 手机视口，不能替代现场试用。
- 保留既有工作台和其他业务功能，本阶段不是整个 V2 的全部改版。静态 `/demo` 不写入新财务数据；请用本次模拟账号体验。

入口：<http://127.0.0.1:5292/login/sales>，不是 B 的 5291。

账号及本机试用密码见 `outputs/gushios-v2-phase3c/试用账号.md`。四个账号使用同一登录页，按实际授权进入工作台。试用数据来自 B 模拟库副本，另外新增“试用｜材料供应与垫资”、两批交付、部分预付、确认/不确定回款、工资、租金和报销。旧模拟合同和逾期计划也参与汇总，因此看板不只包含这一条新项目。

建议验收顺序：

1. 销售登录 → 项目协同 → “试用｜材料供应与垫资” → 项目收支，提交报销或回款信息，确认无法查看采购成本及公司现金。
2. 财务登录 → 首页现金流，切换情景，展开具体周查看缺口来源；进入项目收支，选择审核报销，再确认实际付款。
3. 财务在项目收支登记订单/批次/付款计划，改变预计到货日期，检查建议日期与历史实付。财务确认建议后重新查看现金流。
4. 财务 → 工资和固定费用，参考上月生成草稿，再确认；实际发薪与预算不同时勾选结清，核对待付余额移除、原预算保留。
5. 管理 → 现金流与资金风险，查看垫资风险和 13 周明细，确认没有余额或实际收付款修改表单。
6. 管理可在项目收支中单独授权协作者提交报销；协作者通过“项目报销”入口操作，不能因此读取完整销售项目。
