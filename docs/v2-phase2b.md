# GushiOS V2.0 第二阶段 B 交付记录

验收日期：2026-11-10。基于阶段 A，在 `codex/gushios-v2` 开发。本次只交付业务状态、原因历史、个人结果和暂停复查；未合并 main、未部署，也未启动第三阶段。

## 已实现

- 业务状态统一为跟进中、已成交、已暂停、已丢单；原工程阶段独立保留，作为补充资料。
- 暂停、丢单只需选择原因分类并填写一句说明；建议、竞争对手、暂停复查日期可展开选填。前端和后端独立验证，旧项目编辑接口不能绕过原因校验。
- 状态、原始原因、操作事件和站内通知在同一数据库事务中保存。并发修改返回冲突，失败整体回滚，不出现状态已变但原因丢失。
- 原因事件记录当时项目名称、负责人 memberId、操作人、服务器时间和状态变化。补充、更正追加版本，保留原文；恢复项目和转交不删除历史。
- 销售侧栏“我的项目结果”；管理侧栏“员工结果与复查”。当前状态数量与历史事件分开，暂停和丢单分开，独立项目数量按项目 ID 去重，不自动扣绩效。
- 转交后原销售只能读自己任期的结果快照，不能读取当前项目或转交后的原因更正。财务可读项目原因，不能改状态、原因或负责人，也没有其他销售个人档案入口。
- 暂停项目退出普通跟进逾期列表。管理首页提供到期复查入口；有日期按日期，无日期默认 7 天，可配置 1–90 天。按上海自然日判断，到期当天进入清单。
- 管理可提出异议、要求补充、继续观察或恢复项目；意见留存并通知负责人。暂停和丢单保存无需等待审核。
- 状态、原因、管理复查和普通资料编辑均不刷新真实跟进时间。阶段 A 的快速跟进、最少字段创建、合同提交和财务隔离继续保留。

## 数据兼容与风险

沿用第一阶段已有的结果事件、更正、负责人历史和管理复查表，没有新增破坏性 schema 迁移。项目 JSON 只增加可选元数据，原 ID、账号、工程阶段、消息、合同、财务及任务保留；未清空原预览数据库。

没有业务状态的旧项目按原阶段兼容读取：已暂停/已丢单保持对应状态，合同履约/售后复盘/已结项视为已成交，其他视为跟进中。旧模拟项目没有原因时不编造历史原因；没有状态时间的旧项目以已有更新时间作为复查起点。本次仍不是需要真实历史数据迁移的生产升级。

原销售冻结快照以首次转交时间作为更正可见性截止点。极端情况下同一毫秒发生的更正和转交，原销售端保守隐藏该更正，原始原因和管理可见的完整历史不丢失。未来若要严格排序同毫秒操作，可增加独立事件序列；当前优先防止转交后信息泄露。

本次复制阶段 A 的模拟库为独立 B 试用库，并保留 trial-before.sqlite 备份。B 库新增明确标注“试用｜”的到期暂停、未设日期暂停、价格丢单和已转交历史示例，自动化也创建了模拟项目。原账号密码及原预览库未修改。

## 本机试用

地址：<http://127.0.0.1:5291/login/sales>。使用 `outputs/gushios-v2-phase2b/试用账号.md` 中的销售甲、销售乙、管理、财务账号；同一个登录页会按真实授权进入对应工作台。旧 5180、阶段 A 的 5290 不是本次 B 入口。

销售：打开本人项目 → 修改状态 → 选择暂停或丢单 → 分类加一句说明 → 保存。可展开补充信息设置复查日期，再在“状态与原因”查看或更正原记录。“我的项目结果”查看历史；转交示例只显示快照，不提供当前项目访问。

管理：首页“查看暂停复查” → 选择到期项目 → 填写意见并选择处理方式。侧栏“员工结果与复查”可按员工查询，并设置无指定日期项目的周期。恢复项目后，原暂停原因仍能查看。

财务：项目协同 → 打开项目 → 状态与原因，确认可读且没有状态修改、更正入口。原合同与票款功能继续使用。

服务退出后双击证据目录中的 `启动阶段B试用.command`。该服务只监听本机，不是互联网演示链接。
